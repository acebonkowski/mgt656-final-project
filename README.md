# mgt656-final-project

Event discovery app for Yale graduate students (MGT656 final project). Django + PostgreSQL (Supabase), deployed on Render.

Onboarding now shares the authentication profile, seeds provisional Yale degree
choices, and supports private object-storage photos. See
[onboarding setup and release checks](docs/onboarding-development.md), including
the required storage environment variables and `setup_photo_storage` command.

## Local development

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
export DJANGO_DEBUG=true          # SQLite + dev secret key, local only
.venv/bin/python manage.py migrate
.venv/bin/python manage.py seed   # grader accounts (safe to run again)
.venv/bin/python manage.py runserver
```

To use Postgres locally, also export `DATABASE_URL` (see [.env.example](.env.example)).

## Tests

```bash
DJANGO_DEBUG=true .venv/bin/python manage.py test
```

Tests never touch external services: the health check's database failure is mocked, settings tests only parse fake URLs, and login emails are captured in memory by Django's test runner (send failures are mocked).

## Configuration

All configuration comes from environment variables. Nothing secret is committed. [.env.example](.env.example) lists every variable, with placeholders only.

| Variable | Required on Render | Notes |
|----------|-------------------|-------|
| `DATABASE_URL` | yes | Supabase **Session pooler** string (port 5432) |
| `DJANGO_SECRET_KEY` | yes | Generated by the Render blueprint |
| `APP_ENV` | yes | `staging` or `production` (set by the blueprint) |
| `DJANGO_DEBUG` | no | Defaults to `false` |
| `DJANGO_ALLOWED_HOSTS` / `DJANGO_CSRF_TRUSTED_ORIGINS` | no | The Render hostname is added automatically; use these for custom domains |
| `PORT` | set by Render | gunicorn binds to it |
| `TEAM_NICKNAME` | no | Team course nickname; defaults to `holy-dew`. Holds the nickname, never the hash |
| `TEAM_MEMBER_NICKNAMES` | no | Comma-separated member nicknames shown on the A/B page |
| `MAP_API_KEY` | no | Optional server-side MapTiler key for address autocomplete. The local OSM basemap works without it. |
| `RESEND_API_KEY` | for login emails | Resend API key, used as the SMTP password. Without it, deployed environments don't send codes (students see an error); local development prints emails to the terminal |
| `EMAIL_FROM` | for login emails | Sender on the team's verified Resend domain, e.g. `Yale Events <login@mail.<domain>>` |
| `EMAIL_PORT` | no | Defaults to `587`; Resend also accepts `2587` |
| `GRADER_FIXED_OTP` | for grader login | Fixed 6-digit code for the seeded grader accounts. Same value on staging and production. Never commit it |
| `OPENROUTER_API_KEY` | for AI features | OpenRouter key from the course credits. Server-side only: never commit it or expose it to browser JavaScript. Tests mock the LLM, so they don't need it |
| `OPENROUTER_MODEL` | for AI features | Use `google/gemini-3.1-flash-lite` (text, image and audio input, structured output, low cost). Verify key + model on an environment with `python manage.py check_openrouter` (sends one tiny request, uses credits) |

## A/B test page

The course-required A/B page lives at `/` + the first 7 hex characters of `sha1(TEAM_NICKNAME)`, hashed with no trailing newline (`printf %s holy-dew | shasum`, **not** `echo`). For `holy-dew` that's:

- Page: `/e75d81f`. Each new visitor gets `kudos` or `thanks` (50/50, kept in the session). One impression is counted per visitor and at most one click.
- Stats: `/e75d81f/stats`. Live JSON with counts and `preferred`, the variant with the higher click rate. With no data or a tie, `preferred` is `kudos`.

The code is in [abtest/](abtest/). Impressions and clicks can be viewed (and test visits deleted) in the Django admin under **A/B test**.

## Login (`/login/`)

Students log in with a one-time code emailed to their Yale address (#6); there are no passwords. It's built on Django's normal auth and sessions; the code is in [accounts/](accounts/).

- `/` sends logged-out visitors to the **Welcome** screen (`/login/`) and logged-in users to the map.
- Only `@yale.edu` addresses and its subdomains (e.g. `@som.yale.edu`) are accepted, checked on the server.
- Codes are 6 digits, valid for 10 minutes, work once and stop working after 5 wrong tries. Only a keyed hash is stored. A new code can be sent after 45 seconds (enforced on the server).
- A new address creates an account and goes to onboarding (`/onboarding/`, a placeholder until #7). An existing user with a completed profile goes to the map.
- Log out with the button on the map.

### Grader accounts and the seed command

`python manage.py seed` creates or updates the grader accounts. It's safe to run more than once; run it after every database reset and after the first deploy of an environment:

| Account | Role |
|---------|------|
| `kyle.jensen@yale.edu` | Admin (staff + superuser, can open `/admin`) |
| `mgt656-demo-member@yale.edu` | Member (regular student) |

Graders log in on the Welcome screen with the fixed code from `GRADER_FIXED_OTP` (per Kyle). They never receive email, the code works for no other address, and 5 wrong tries lock the address for 15 minutes. The accounts have no password: `/admin`'s login page redirects to the Welcome screen, and Kyle's account opens `/admin` once logged in.

On Render the seed runs automatically on every start, right after `migrate` ([bin/start.sh](bin/start.sh)), so a restart re-creates the accounts after a database reset. To run it by hand, run `python manage.py seed` with that environment's `DATABASE_URL` exported.

### Email (Resend)

Codes are sent through Resend's SMTP relay using Django's built-in SMTP backend (`smtp.resend.com`, user `resend`, the API key as the password). Resend only delivers to any address from a **domain the team controls and has verified** (SPF/DKIM DNS records), so `EMAIL_FROM` must use that domain.

## Home screen map (`/map/`)

`/map/` is the logged-in home screen: a New Haven map with the headline "More coming soon." (#8). Logged-out visitors are sent to the Welcome screen (`LOGIN_URL`). `LOGIN_REDIRECT_URL` and `ONBOARDING_SUCCESS_URL` both point to `map`.

The map uses locally stored OpenStreetMap vector tiles in [core/data/new-haven.mbtiles](core/data/new-haven.mbtiles), covering New Haven at zoom levels 8–16. The archive was generated from the Connecticut Geofabrik OSM extract (2026-11-17) with the Planetiler OpenMapTiles profile. It is rendered by the locally vendored MapLibre GL JS 5.24.0 library. The app serves tiles from the local MBTiles archive, so displaying the map does not require MapTiler, a map API key, or external tile requests. The visible attribution credits © OpenMapTiles and © OpenStreetMap contributors. OSM data is available under ODbL 1.0; the generated vector tiles are reusable under CC-BY as granted by OpenMapTiles.

- [templates/core/_map_provider.html](templates/core/_map_provider.html) loads the local MapLibre assets and provider script.
- [core/static/core/map_provider.js](core/static/core/map_provider.js) defines `window.renderMap(element, config)` and styles the local OSM vector layers.
- [core/views.py](core/views.py) serves MBTiles vector data at `/map/tiles/{z}/{x}/{y}.pbf`.

The provider-neutral [core/static/core/map.js](core/static/core/map.js) calls `renderMap`. It shows the fallback message if the local archive is missing, MapLibre didn't load, or the browser has no WebGL.

The map also shows a curated Yale-area place layer: Yale facilities (including Yale School of Management / Evans Hall), restaurants, and bars use distinct icons and popup labels. Coordinates are maintained in [core/map_places.py](core/map_places.py), sourced from OpenStreetMap (© OpenStreetMap contributors, ODbL 1.0); the list is static and makes no runtime geocoding requests. Verify places and coordinates before extending the list.

`MAP_API_KEY` is no longer needed to display the map. It is used only by the server-side MapTiler geocoding request for address autocomplete, so autocomplete requires the key and network access. The basemap itself is served locally. `NoNetworkTests` fails if rendering the page opens any network connection.

### Optional MapTiler key for address autocomplete

1. Sign up at [cloud.maptiler.com](https://cloud.maptiler.com/) (the free plan needs no credit card).
2. Go to **Account → API keys** and create a key for geocoding.
3. In Render, open the service, go to **Environment**, and set `MAP_API_KEY` to the key. Saving restarts the service.
4. To test autocomplete locally, set the key in the same terminal as `runserver` (the app doesn't read `.env` files):
   - macOS/Linux: `export MAP_API_KEY=<key>`
   - Windows PowerShell: `$env:MAP_API_KEY = "<key>"`

Without this key, the local map still works but location autocomplete is unavailable. Never commit a key; keep it in your shell or in Render only.

## Deploying (staging and production)

- **Staging:** https://mgt656-final-project-staging.onrender.com (health check: [/healthz](https://mgt656-final-project-staging.onrender.com/healthz))
- **Production:** https://mgt656-final-project-y89o.onrender.com (health check: [/healthz](https://mgt656-final-project-y89o.onrender.com/healthz))

[render.yaml](render.yaml) defines two free web services, `mgt656-staging` (auto-deploys on every push to `main`) and `mgt656-production` (manual deploys only). On every start, [bin/start.sh](bin/start.sh) runs `migrate`, then `seed`, then gunicorn on `$PORT`, with access and error logs going to stdout. Render's pre-deploy command needs a paid plan, so migrations run at start instead.

One-time setup (done by a team member with the accounts):

1. **Supabase:** create two projects, e.g. `mgt656-staging` and `mgt656-production`, in region **West US (Oregon)** (us-west-2), the same region as the Render services. For each one, go to **Connect** and choose **Session pooler**, then copy the URI (`postgresql://postgres.<ref>:<password>@aws-1-us-west-2.pooler.supabase.com:5432/postgres`).
   - Use the session pooler, not the direct connection. Render has no outbound IPv6, and Supabase's direct host is IPv6-only unless you buy the IPv4 add-on.
2. **Render:** go to **New**, then **Blueprint**, and select this repo. When prompted, paste each service's own `DATABASE_URL`: the staging URL into `mgt656-staging` and the production URL into `mgt656-production`.
3. Open `https://<service>.onrender.com/healthz`. It should return `{"status": "ok", "database": "ok"}`.

`/healthz` is also Render's health check. It returns `503` if the database can't be reached, so a deploy with a bad `DATABASE_URL` won't go live.

### CI/CD (#43)

- **CI** ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on every pull request and every push to `main`: `ruff check`, a missing-migrations check, then the test suite. Branch protection on `main` requires the **Lint and test** check, so a failing PR can't be merged. Run it locally with `.venv/bin/pip install -r requirements-dev.txt && .venv/bin/ruff check . && DJANGO_DEBUG=true .venv/bin/python manage.py test`.
- **Staging** deploys automatically from `main` once CI passes (`autoDeployTrigger: checksPass` in [render.yaml](render.yaml)). If CI fails on `main`, staging is not deployed.
- **Production** is promoted deliberately, as the brief requires. Go to **Actions**, open **Promote to production**, click **Run workflow** on `main` and enter a reason. The workflow re-runs CI on that commit, checks staging `/healthz`, triggers the production Render deploy hook for that exact commit, then checks production `/healthz`. Production never deploys on merge.

One-time setup (repo owner):

1. Render → `mgt656-production` → **Settings** → **Deploy Hook**: copy the URL. In GitHub → **Settings** → **Secrets and variables** → **Actions**, add it as `RENDER_PRODUCTION_DEPLOY_HOOK`. Never commit it: anyone with the URL can deploy.
2. GitHub → **Settings** → **Branches**: protect `main`, require a pull request and the **Lint and test** status check.
3. Optional: GitHub → **Settings** → **Environments** → `production`: add required reviewers so a promotion needs a second click to approve.

## Automated event imports (#33)

The importer reads Yale Connect and SOM ICS feeds and, when configured, the
Ticketmaster Discovery API. Localist is intentionally excluded until public
access/terms are verified. Unknown prices display **Price not listed**; imported
event pages show the source. Invalid or unsupported events are counted and
skipped instead of receiving invented dates, prices or coordinates.

Set `MAP_API_KEY` for address geocoding and optionally `TICKETMASTER_API_KEY`.
Geocoding uses the existing MapTiler service; confirm the team's plan/quota before
running large imports. Set `AGGREGATOR_TOKEN` to a long random server-side secret.
Migrations create a shared import lock and persistent geocoding cache.

Initial population through December 31, 2026 (exclusive January 1 cutoff):

```sh
python manage.py migrate
python manage.py import_events --until 2027-01-01T00:00:00-05:00
```

Use `--source yale_connect`, `--source som` or `--source ticketmaster` to narrow
the run; repeat the option for multiple sources. Repeat runs are safe. The
runtime budget defaults to 180 seconds (`AGGREGATOR_RUN_SECONDS`, maximum 300).
If logs show `deadline_reached`, rerun to continue: already imported identities
are skipped. The automatic job uses a rolling 90-day window (`AGGREGATOR_WINDOW_DAYS`,
maximum 365). The CLI defaults to the initial year-end cutoff; use `--until`
for other windows after that period.

### Daily cron-job.org setup

Create a free cron-job.org job for each environment to import:

- URL: `https://<your-service-host>/internal/import-events/`
- Method: **POST**, no body required.
- Header: `Authorization: Bearer <the environment's AGGREGATOR_TOKEN>`.
- Schedule: daily **18:00**, timezone explicitly **America/New_York** (DST-aware).
- Enable failure notifications. Never put the token in a query string or commit it.

The endpoint returns **403** for missing/wrong credentials and **202** immediately
for accepted/already-running jobs. Work happens in a background thread. Check
stdout logs for `event_import start`, per-source progress and `event_import end`
with imported, rejected duplicate, skipped-past and failure counts. A 202 only
acknowledges scheduling; it does not certify completion. This repository does
not provision a cron-job.org account or job automatically.

The shared database lock prevents overlapping workers and CLI runs. If a worker
is killed/redeployed, a lock can remain held. Confirm that worker has stopped,
find its run token in logs, then recover with:

```sh
python manage.py import_events --release-lock <stopped-run-token>
```

Do not release a live worker's lock. Imports retain existing records; source
updates/cancellations do not overwrite existing event identities. Expired events
stay in the database and disappear from the map. A server background thread is
not a durable queue; interruptions require rerunning the idempotent job.

### AI budgets and images

`AGGREGATOR_MAX_IMAGES_PER_RUN=0` and
`AGGREGATOR_MAX_CLASSIFICATIONS_PER_RUN=0` disable paid AI calls by default. After
budget approval, set finite per-run caps to enable the existing server-side
OpenRouter service. Configure an image-capable `OPENROUTER_MODEL` and the existing
Supabase event-photo bucket (use `setup_photo_storage` with the existing project
instructions). Failed requests consume their cap. Image failures and events over
the cap retain a text placeholder; all valid events can still import. LLM
classification is used only after source mapping and keyword rules fail; invalid
or failed AI output falls back to `social_community`.

No API keys or source response bodies are included in import logs. Tests use
saved fixtures and mock HTTP, geocoding, OpenRouter and storage:

```sh
python manage.py test core.tests.test_aggregator core.tests.test_event_import core.tests.test_event_import_persistence
```
